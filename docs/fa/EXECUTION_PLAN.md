# برنامه اجرایی محصول و مهندسی

**مبنای برنامه:** استراتژی SaaS عمومی، Visual Agent Builder، Multi-provider و Closed Beta  
**تاریخ تصویب:** 2026-11-01  
**وضعیت:** برنامه مصوب؛ زمان‌بندی‌ها تخمینی و وابسته به ظرفیت توسعه‌اند.

## قواعد اجرای برنامه

- هر فاز با یک PR کوچک و قابل‌بازبینی یا مجموعه‌ای از PRهای مرتبط انجام شود.
- هر قابلیت باید معیار پذیرش و تست متناظر داشته باشد.
- وضعیت «پیاده‌سازی‌شده»، «تست‌شده» و «فعال در Production» جداگانه گزارش شود.
- هیچ تغییری روی `main`، Merge یا Deploy بدون تأیید جداگانه انجام نشود.
- قبل از شروع فاز بعد، معیارهای خروج فاز جاری بررسی شوند.

## فاز 0 — تثبیت و آمادگی پایه

**اولویت: فوری**

کارها:
- بررسی وضعیت CI و رفع تست‌های ناپایدار.
- بازبینی کنترل دسترسی owner-scoped برای Agent و Task.
- افزودن rate limiting و محدودیت ورودی/خروجی در نقاط پرهزینه.
- بازبینی نشست‌ها، ذخیره توکن، CORS و سیاست امنیتی مرورگر.
- افزودن تست‌های end-to-end برای ثبت‌نام، ورود، ساخت Agent و اجرای Task.
- اطمینان از صحت migrationها، backup و restore.
- روشن‌کردن وضعیت Provider در داشبورد بدون افشای اطلاعات محرمانه.

معیار خروج:
- CI سبز روی آخرین commit فاز.
- تست مالکیت منابع و مسیرهای خطا موفق.
- چک‌لیست امنیتی پایه تکمیل و موارد باقیمانده ثبت شده.
- قابلیت اجرای واقعی AI فقط در محیطی فعال شود که Provider خصوصی و معتبر پیکربندی شده باشد.

## فاز 1 — Visual Agent Builder

**اولویت: بسیار بالا**

Frontend:
- فرم ساخت و ویرایش Agent با فیلدهای نام، توضیحات، هدف و دستورالعمل.
- انتخاب Provider و مدل از گزینه‌های مجاز دریافت‌شده از Backend.
- نمایش اعتبارسنجی، پیش‌نمایش خلاصه تنظیمات و وضعیت Draft/Active/Paused.
- الگوهای شروع سریع و راهنمای کوتاه برای کاربران تازه‌کار.
- حالت‌های loading، empty، error و unsaved changes.

Backend:
- schema نسخه‌دار برای پیکربندی Agent.
- اعتبارسنجی سمت سرور و محدودیت طول/اندازه فیلدها.
- ذخیره انتخاب Provider و model identifier.
- اعمال مالکیت و مجوز در تمام عملیات.
- جلوگیری از فعال‌سازی Agent با Provider یا مدل نامعتبر/غیرفعال.

معیار خروج:
- کاربر بدون ویرایش JSON یا نوشتن کد بتواند Agent بسازد، ویرایش کند، ذخیره کند و اجرا کند.
- تست API برای validation، مالکیت و چرخه وضعیت.
- تست مرورگر برای جریان کامل ساخت تا اولین اجرا.

## فاز 2 — لایه Multi-provider

**اولویت: بسیار بالا؛ می‌تواند موازی با بخش‌هایی از فاز 1 توسعه یابد.**

کارها:
- تعریف قرارداد داخلی Provider Adapter.
- پیاده‌سازی adapter نخست و adapter دوم پس از انتخاب سرویس‌های واقعاً در دسترس.
- endpoint امن برای فهرست Provider/modelهای فعال و قابلیت‌هایشان.
- timeout، retry policy متناسب با نوع خطا و نگاشت خطاهای استاندارد.
- ثبت latency، token usage و هزینه تخمینی وقتی Provider این داده‌ها را ارائه می‌کند.
- تست contract با mock server؛ CI به حساب‌های واقعی Provider وابسته نباشد.
- نگهداری کلیدها در secret manager محیط Backend.

معیار خروج:
- افزودن Provider جدید بدون تغییر منطق اصلی Agent runtime امکان‌پذیر باشد.
- خطاهای Provider به پیام قابل‌فهم و قابل‌اقدام در UI تبدیل شوند.
- هیچ secret در Frontend، response یا log ظاهر نشود.

## فاز 3 — Runtime قابل‌اعتماد و کنترل مصرف

**اولویت: بالا**

کارها:
- صف پایدار و worker برای اجرای Task.
- state machine شامل queued، running، succeeded، failed، cancelled و در صورت نیاز awaiting_approval.
- idempotency، lease recovery، cancellation و retry کنترل‌شده.
- سقف زمان، اندازه ورودی/خروجی، تعداد تلاش و بودجه مصرف.
- ثبت رویدادهای ممیزی و trace هر اجرا.
- جلوگیری از اجرای هم‌زمان یا تکراری ناخواسته.
- داشبورد وضعیت زنده و تاریخچه صفحه‌بندی‌شده.

معیار خروج:
- تست خرابی worker، انقضای lease، retry و cancellation.
- اجرای مجدد درخواست باعث side effect تکراری کنترل‌نشده نشود.
- هزینه و زمان اجرا قابل‌اندازه‌گیری باشد.

## فاز 4 — Workflow Engine و ابزارهای محدود

**اولویت: متوسط تا بالا؛ پس از تثبیت runtime**

کارها:
- مدل workflow نسخه‌دار با stepهای typed و وابستگی مشخص.
- ابتدا اجرای ترتیبی؛ branching و موازی‌سازی فقط پس از نیازسنجی.
- timeout، سقف تعداد step، سقف بودجه و امکان توقف.
- Tool Registry با schema ورودی/خروجی نسخه‌دار.
- allowlist ابزارها، مجوزهای حداقلی، نگهداری امن credential و امکان لغو دسترسی.
- تأیید انسانی برای عملیات حساس.
- دفاع در برابر prompt injection، SSRF و محتوای بیرونی نامطمئن.
- ابزارهای mock برای تست CI.

معیار خروج:
- Workflow قابل‌توقف و قابل‌ردیابی باشد.
- هیچ ابزار یا عملیات خارجی بدون مجوز صریح قابل‌اجرا نباشد.
- تست امنیتی و مالکیت برای Workflow و Toolها موفق باشد.

## فاز 5 — Usage, Quotas و آماده‌سازی SaaS

**اولویت: بالا؛ قبل از پرداخت واقعی**

کارها:
- ثبت usage به تفکیک user، task، provider و model.
- تعریف entitlement و quota سمت سرور.
- سقف اجرا، مصرف و هم‌زمانی برای هر پلن.
- هشدار نزدیک‌شدن به سهمیه و تجربه روشن پس از اتمام سهمیه.
- محاسبه هزینه تقریبی و حاشیه امن برای هر پلن.
- صفحه شفاف پلن‌ها و مصرف.
- تست race condition برای جلوگیری از عبور هم‌زمان درخواست‌ها از سهمیه.

معیار خروج:
- سهمیه‌ها فقط در Backend enforce شوند.
- گزارش مصرف با داده‌های ثبت‌شده سازگار باشد.
- هزینه بدترین حالت قابل‌برآورد و کنترل باشد.

## فاز 6 — Billing و اشتراک

**اولویت: بعد از اثبات هزینه و تقاضا**

کارها:
- انتخاب ارائه‌دهنده پرداخت متناسب با کشور/بازار هدف و امکان قانونی استفاده.
- طراحی subscription lifecycle، webhook verification و idempotency.
- مدیریت تمدید، لغو، شکست پرداخت و بازپرداخت.
- اتصال وضعیت پرداخت به entitlementهای Backend.
- نگهداری سوابق مالی و لاگ قابل‌ممیزی.
- سیاست حریم خصوصی، شرایط استفاده و فرایند پشتیبانی.

معیار خروج:
- تست webhookهای تکراری/نامعتبر و تغییر وضعیت اشتراک.
- کاربر با پرداخت ناموفق دسترسی پولی اشتباه دریافت نکند.
- پلن و quota در UI و Backend همسان باشند.

## فاز 7 — Closed Beta

**اولویت: پس از عبور از دروازه‌های کیفیت**

گام‌ها:
1. تست داخلی با داده آزمایشی.
2. دعوت 5 تا 10 کاربر اولیه با سقف مصرف محدود.
3. مصاحبه و ثبت frictionهای onboarding.
4. رفع خطاهای بحرانی و بهبود قابلیت استفاده.
5. گسترش کنترل‌شده به 20 تا 50 نفر در صورت پایداری.
6. بررسی شاخص‌ها و تصمیم جداگانه برای عرضه عمومی.

معیار خروج:
- ثبت‌نام و onboarding قابل‌فهم.
- نرخ موفقیت Task و نرخ خطای Provider در محدوده هدف تیم.
- هزینه هر اجرای موفق اندازه‌گیری شده.
- رخداد امنیتی بحرانی باز وجود نداشته باشد.
- پشتیبانی، گزارش مشکل و راهکار rollback آماده باشد.

## فاز 8 — آمادگی عرضه عمومی

- تست بار و ظرفیت.
- بازبینی امنیتی مستقل و dependency scanning.
- بررسی دسترس‌پذیری و تجربه موبایل.
- backup/restore drill و runbook رخداد.
- مانیتورینگ، alert و سیاست retention داده.
- انتشار release notes و مستندات کاربر.
- تصمیم go/no-go بر اساس داده‌های Closed Beta.

## برنامه زمانی تخمینی

| بازه | تمرکز اصلی |

| هفته 3–4 | Visual Agent Builder و Provider abstraction |

این زمان‌بندی تعهد انتشار نیست؛ در صورت وجود نقص امنیتی، تست ناموفق یا وابستگی بیرونی، فاز مربوطه متوقف می‌شود.

## دروازه‌های تصمیم

- **Gate A:** قبل از اجرای مدل واقعی، Provider خصوصی، timeout و سقف مصرف باید آماده باشند.
- **Gate B:** قبل از ابزارهای خارجی، permission scopes، audit log و human approval باید آماده باشند.
- **Gate C:** قبل از دریافت وجه، usage metering، quota enforcement و هزینه واحد باید قابل‌اعتماد باشند.
- **Gate D:** قبل از Closed Beta، پشتیبانی، مانیتورینگ، backup و rollback باید آزموده شوند.
- **Gate E:** عرضه عمومی نیازمند تصمیم جداگانه و شواهد موفقیت بتاست.
