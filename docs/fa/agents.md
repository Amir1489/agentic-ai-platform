# API عامل‌ها و اجرای پس‌زمینه وظایف

تمام مسیرهای این سند به توکن Bearer معتبر نیاز دارند.

## پیکربندی عامل
- `GET /api/agents` — فهرست عامل‌های متعلق به کاربر جاری.
- `POST /api/agents` — ایجاد عامل با وضعیت `draft`.
- `PUT /api/agents/{agent_id}` — به‌روزرسانی پیکربندی و وضعیت چرخه عمر.
- `DELETE /api/agents/{agent_id}` — حذف عامل متعلق به کاربر.

فیلدهای ایجاد/ویرایش:
- `name`: اجباری، ۱ تا ۱۰۰ نویسه.
- `description`: اختیاری، حداکثر ۵۰۰ نویسه.
- `instructions`: دستورالعمل سیستمی اختیاری، حداکثر ۴٬۰۰۰ نویسه.
- `model`: شناسه مدل ارائه‌دهنده، حداکثر ۱۰۰ نویسه.
- `status`: هنگام ویرایش یکی از `draft`، `active` یا `paused`.

تمام جست‌وجوها به شناسه کاربر احراز هویت‌شده محدود هستند. عامل کاربر دیگر به شکل not found گزارش می‌شود.

## ثبت و اجرای یک Task
۱. مقدار `AI_API_KEY` را به‌صورت محرمانه در محیط بک‌اند تنظیم کنید.  
۲. وضعیت عامل را `active` کنید.  
۳. درخواست `POST /api/agents/{agent_id}/tasks` را با JSON زیر بفرستید:

```json
{"input":"Summarize the supplied topic..."}
```

در صورت معتبر بودن درخواست، API با HTTP 202 کار را در پایگاه داده با وضعیت `queued` ثبت می‌کند و بلافاصله پاسخ می‌دهد. Worker پس‌زمینه صف پایگاه داده را بررسی می‌کند، کار را به‌صورت اتمی از `queued` به `running` می‌برد و سپس مدل را فراخوانی می‌کند.

چرخه وضعیت فعلی:
- `queued`: ثبت شده و منتظر Worker.
- `running`: توسط یک Worker دریافت شده است.
- `succeeded`: پاسخ مدل ذخیره شده است.
- `failed`: اجرای کار ناموفق بوده است.

## پیگیری و تاریخچه
- `GET /api/agents/{agent_id}/tasks` — حداکثر ۵۰ کار اخیر.
- `GET /api/agents/{agent_id}/tasks/{task_id}` — وضعیت و نتیجه یک کار.
- `GET /api/agents/{agent_id}/tasks/{task_id}/events` — رویدادهای مرتب‌شده اجرا.

رویدادهای فعلی شامل `queued`، `started`، `succeeded` و `failed` هستند. داشبورد پس از ثبت کار، مسیر جزئیات را برای دریافت وضعیت نهایی بررسی می‌کند.

## محدودیت‌های اجرا
- ورودی: حداکثر ۸٬۰۰۰ نویسه.
- دستورالعمل سیستم: حداکثر ۴٬۰۰۰ نویسه.
- خروجی: حداکثر ۱۲٬۰۰۰ نویسه.
- مهلت HTTP ارائه‌دهنده: ۴۵ ثانیه.
- هر Task فقط یک فراخوانی مدل انجام می‌دهد.
- فقط عامل فعال و متعلق به کاربر قابل صف‌بندی است.
- اگر ارائه‌دهنده هنگام ثبت Task پیکربندی نشده باشد، درخواست با HTTP 503 رد می‌شود.

## رفتار Worker و محدودیت‌های عملیاتی
- صف در جدول `agent_tasks` ذخیره می‌شود؛ بنابراین ثبت Task به حافظه فرایند وابسته نیست.
- هر نمونه API یک حلقه Worker سبک در چرخه عمر FastAPI اجرا می‌کند.
- دریافت Task با به‌روزرسانی شرطی وضعیت انجام می‌شود تا دو نمونه Worker یک Task را هم‌زمان دریافت نکنند.
- فراخوانی مدل بیرون از تراکنش پایگاه داده انجام می‌شود.
- هنگام خاموش‌شدن تمیز برنامه، حلقه Worker لغو می‌شود.
- هنوز lease/heartbeat برای بازیابی Taskهایی که فرایند پس از claim شدن متوقف می‌شود وجود ندارد؛ چنین Taskی ممکن است در وضعیت `running` باقی بماند.
- لغو کار، تلاش مجدد خودکار، صف اولویت‌دار، محدودیت هزینه/توکن، worker مجزا و هماهنگ‌سازی چندمرحله‌ای هنوز پیاده‌سازی نشده‌اند.

## ایمنی
این نسخه اجرای ابزار دلخواه، shell، کد دلخواه، عملیات مرورگر یا یکپارچه‌سازی خارجی ندارد. برای اقدامات مهم و اثرگذار از این نسخه استفاده نکنید و آن را سرویس عامل خودمختار آماده تولید تلقی نکنید.


## مرحله بعدی: Lease و بازیابی خودکار

این مرحله برای رفع Taskهای باقی‌مانده در وضعیت `running` پس از توقف ناگهانی Worker تأیید شده است، اما هنوز پیاده‌سازی نشده است. معیارهای پذیرش شامل lease با انقضا، شناسه Worker، heartbeat، بازیابی Task منقضی‌شده، سقف تلاش، رویدادهای ممیزی و آزمون رقابت چند Worker است. تا زمان تکمیل و موفقیت CI، رفتار بازیابی خودکار در دسترس نیست.
