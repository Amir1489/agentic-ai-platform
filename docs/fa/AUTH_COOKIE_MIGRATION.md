# پیشنهاد مهاجرت احراز هویت به Cookie امن

**وضعیت:** فقط پیشنهاد معماری؛ هنوز پیاده‌سازی نشده است  
**تاریخ:** ۲۰۲۶-۱۱-۰۱  
**دامنه کار:** جایگزینی Bearer Token ذخیره‌شده در مرورگر با Cookie نشست مدیریت‌شده در سرور.

## ۱. وضعیت فعلی و تصمیم معماری

فرانت‌اند فعلی روی `https://amir1489.github.io` و API به‌صورت جداگانه روی Render میزبانی می‌شود. فرانت‌اند توکن Bearer را در `localStorage` نگه می‌دارد و در هدر `Authorization` می‌فرستد.

تبدیل مستقیم این ساختار به Cookie بین دامنه `github.io` و دامنه `onrender.com` راهکار قابل اتکایی برای Production نیست؛ زیرا به رفتار کوکی‌های شخص ثالث وابسته می‌شود و بعضی مرورگرها یا تنظیمات حریم خصوصی آن‌ها را مسدود می‌کنند.

**تصمیم پیشنهادی:** پیش از فعال‌سازی Cookie در Production، فرانت‌اند و API باید روی زیردامنه‌های HTTPS یک دامنه قابل‌کنترل توسط مالک پروژه قرار بگیرند. نمونه فرضی:

- فرانت‌اند: `https://app.example.com`
- API: `https://api.example.com`

این آدرس‌ها صرفاً مثال‌اند و هنوز تنظیم نشده‌اند. تا آماده و آزمایش‌شدن این پیش‌نیاز، استقرار فعلی و روش Bearer بدون تغییر باقی می‌مانند.

## ۲. قرارداد Cookie نشست

پس از آماده‌شدن دامنه مشترک:

- نام Cookie نشست: `__Host-agentic_session`
- ویژگی‌ها: `Secure`، `HttpOnly`، `Path=/` و `SameSite=Lax`.
- حداکثر عمر Cookie نباید از عمر فعلی نشست، یعنی هفت روز، بیشتر شود.
- ویژگی `Domain` نباید تنظیم شود. پیشوند `__Host-` مستلزم Secure، مسیر ریشه و نبود Domain است.
- در دیتابیس فقط digest رمزنگاری‌شده توکن تصادفی نشست ذخیره شود؛ مقدار خام توکن هرگز ذخیره یا log نشود.
- Cookie فقط برای میزبان API معتبر باشد و JavaScript فرانت‌اند نباید آن را بخواند.
- درخواست‌های فرانت‌اند به API از Fetch با `credentials: 'include'` استفاده کنند.
- توکن نشست نباید در localStorage، sessionStorage، URL یا state پایدار فرانت‌اند ذخیره شود.

## ۳. محافظت CSRF و اعتبارسنجی مبدأ

HttpOnly فقط مانع خواندن Cookie نشست توسط JavaScript می‌شود و به‌تنهایی جلوی CSRF را نمی‌گیرد.

کنترل‌های لازم:

۱. هدر `Origin` در تمام درخواست‌های تغییردهنده وضعیت با allowlist دقیق بررسی شود. مبدأ ناشناخته رد شود و هیچ تطبیق wildcard وجود نداشته باشد.

۲. از توکن CSRF وابسته به نشست استفاده شود. پیشنهاد اولیه، تولید توکن با HMAC و کلید محرمانه سمت سرور بر پایه راز نشست احرازشده است. مسیر `GET /api/auth/csrf` توکن را با `Cache-Control: no-store` برگرداند و مرورگر آن را در هدر `X-CSRF-Token` درخواست‌های تغییردهنده وضعیت ارسال کند. API باید هدر، Cookie مخصوص CSRF و مقدار مورد انتظار وابسته به نشست را با مقایسه ثابت‌زمان بررسی کند.

۳. Cookie مربوط به CSRF با نام `__Host-agentic_csrf` و ویژگی‌های `Secure`، `SameSite=Lax` و `Path=/` تنظیم شود. این Cookie برخلاف Cookie نشست HttpOnly نیست؛ اما فرانت‌اند مقدار توکن را از پاسخ endpoint دریافت می‌کند و تلاش نمی‌کند Cookie متعلق به میزبان API را مستقیماً بخواند.

۴. تمام درخواست‌های تغییردهنده وضعیت برای نشست احرازشده، از جمله خروج، به CSRF نیاز دارند. برای ورود و ثبت‌نام نیز اعتبارسنجی سخت‌گیرانه Origin انجام شود تا خطر Login CSRF کاهش یابد.

۵. CORS جایگزین CSRF نیست.

روش دقیق تولید و چرخش توکن CSRF باید پیش از پیاده‌سازی نهایی و همراه با تست بازبینی شود.

## ۴. قرارداد CORS و Fetch

برای مبدأ Production فرانت‌اند:

- `CORS_ORIGINS` فقط شامل origin دقیق مانند `https://app.example.com` باشد.
- CORS با credentials فقط برای originهای دقیق مجاز شود.
- هرگز `Access-Control-Allow-Credentials: true` با origin ستاره‌ای ترکیب نشود.
- فقط متدها و هدرهای لازم، از جمله `Content-Type` و `X-CSRF-Token` مجاز باشند.
- درخواست‌های preflight از نوع OPTIONS درست پاسخ داده شوند.
- ورود، ثبت‌نام، دریافت CSRF، خروج و تمام درخواست‌های احرازشده با `credentials: 'include'` ارسال شوند.
- Cookie نشست روی میزبان API باقی بماند و به دامنه والد گسترش داده نشود.

برای توسعه محلی، بهتر است Vite درخواست‌های `/api` را از طریق proxy هم‌مبدأ به API بفرستد؛ نه اینکه تنظیمات Production ضعیف شوند.

## ۵. رفتار هدف API و نشست

- `POST /api/auth/register` و `POST /api/auth/login`: اعتبارسنجی اطلاعات، ساخت نشست تصادفی فعلی در سرور، تنظیم Cookie HttpOnly و برگرداندن اطلاعات عمومی کاربر به‌همراه اطلاعات لازم برای شروع CSRF. توکن نشست نباید در JSON برگردد.
- `GET /api/auth/me`: احراز هویت از طریق Cookie.
- `GET /api/auth/csrf`: دریافت توکن CSRF غیرقابل cache برای نشست فعلی و تنظیم یا تازه‌سازی Cookie متناظر.
- `POST /api/auth/logout`: الزام CSRF، لغو نشست در دیتابیس و پاک‌کردن هر دو Cookie با همان ویژگی‌های زمان تنظیم.
- تمام routerهای محافظت‌شده از dependency مشترک و سازگار با Cookie استفاده کنند و بررسی مالکیت فعلی منابع حفظ شود.
- انقضای مطلق هفت‌روزه فعلی حفظ شود، مگر اینکه تصمیم جداگانه‌ای برای عمر نشست گرفته شود. انقضای بیکاری و چرخش نشست، سخت‌سازی‌های بعدی‌اند و خودکار وارد این محدوده نمی‌شوند.

## ۶. ترتیب مهاجرت و انتشار

۱. مالک پروژه یک دامنه اختصاصی تهیه و کنترل آن را در اختیار داشته باشد؛ HTTPS برای هر دو زیردامنه app و api فعال شود.

۲. بررسی شود که مبدأ فرانت‌اند و API از نظر مرورگر same-site هستند و DNS، TLS و مسیریابی سفارشی GitHub Pages و Render درست کار می‌کنند.

۳. صدور و اعتبارسنجی Cookie، CSRF، بررسی دقیق Origin، CORS دارای credentials و تست‌های مهاجرت در یک مسیر انتشار کنترل‌شده پیاده‌سازی شوند.

۴. تمام درخواست‌های API فرانت‌اند به credentials مجهز شوند؛ خواندن و نوشتن Bearer Token حذف شود و پس از ورود موفق با Cookie، کلیدهای قدیمی `agentic-auth-token` و `agentic-auth-user` از localStorage پاک شوند.

۵. در زمان انتقال، کاربران فعلی دوباره وارد حساب شوند. توکن‌های قدیمی localStorage نباید به‌عنوان راه میان‌بر به‌صورت پنهانی منتقل شوند.

۶. پیش از فعال‌سازی Cookie در Production، ماتریس پذیرش زیر در محیط staging اجرا شود.

۷. خطاهای احراز هویت، رد CSRF، preflightهای CORS و لغو نشست‌ها پایش شوند؛ بدون ثبت اعتبارنامه یا مقدار توکن در log.

۸. پس از دوره مشاهده مشخص، احراز هویت قدیمی Bearer حذف و مستندات به‌روزرسانی شوند.

این پیشنهاد مجوز تغییر DNS، میزبانی، دامنه سفارشی، تنظیمات محیط Production یا کد احراز هویت نیست.

## ۷. ماتریس پذیرش و تست امنیتی

- ورود و ثبت‌نام ویژگی‌های درست HttpOnly، Secure، SameSite، Path و host-only را تنظیم کنند.
- Cookie نشست برای JavaScript قابل مشاهده نباشد و در JSON برنگردد.
- Cookie معتبر بتواند `/api/auth/me` و routerهای محافظت‌شده را احراز هویت کند.
- Cookie منقضی، لغوشده، نامعتبر یا غایب رد شود.
- خروج نشست را لغو و هر دو Cookie را پاک کند.
- CSRF معتبر پذیرفته شود؛ توکن غایب، نادرست، قدیمی یا متعلق به نشست دیگر رد شود.
- Origin غیرمجاز در ورود، ثبت‌نام و تمام مسیرهای تغییردهنده وضعیت رد شود.
- مبدأ غیرمجاز نتواند پاسخ credentialed را بخواند و CORS wildcard وجود نداشته باشد.
- preflight فقط برای فرانت‌اند مجاز و هدرهای لازم موفق شود.
- تست‌های جداسازی منابع بین حساب‌ها همچنان موفق باشند.
- تست‌های Rate Limiting همچنان موفق باشند.
- migration هم روی دیتابیس تازه و هم دیتابیس در revision قبلی Alembic موفق باشد.
- تست مرورگر روی Chromium، Firefox و WebKit با third-party cookies غیرفعال اجرا شود.

## ۸. بازگشت و ملاحظات عملیاتی

- پیاده‌سازی Bearer فعلی تا موفقیت کامل تست‌های staging دست‌نخورده بماند.
- حالت Cookie فقط با تنظیم صریح Backend فعال شود؛ از روی هدرهای درخواست به‌صورت ضمنی انتخاب نشود.
- در صورت rollback می‌توان جریان Bearer قبلی را بازگرداند، تا وقتی نشست‌های سرور هنوز معتبرند. رکوردهای نشست یا schema بدون migration جداگانه و بازبینی‌شده حذف نشوند.
- مقادیر Cookie، Set-Cookie، Authorization، CSRF، رمز عبور و توکن نشست هرگز log نشوند.
- کلیدهای Provider و اطلاعات اتصال دیتابیس فقط در مخزن محرمانه Backend نگهداری شوند.

## ۹. پیش‌نیازهای باز

- تصمیم مالک پروژه و دسترسی به دامنه اختصاصی.
- تنظیم DNS و TLS برای زیردامنه‌های app و api.
- تأیید پشتیبانی میزبانی انتخاب‌شده از این معماری دامنه.
- بازبینی نهایی روش تولید و چرخش توکن CSRF.
- محیط staging و پوشش تست خودکار مرورگر.

**شرط انتشار:** تا وقتی تمام پیش‌نیازها و تست‌های پذیرش انجام نشده‌اند، احراز هویت Cookie فعال نشود و ادعا نشود ریسک localStorage برطرف شده است.
